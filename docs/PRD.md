## 1. 产品目标（3 个正交目标）

1. **完整可玩的割草闭环**：8 分钟模式与无尽模式双玩法，40 位武将可选，波次→割草→升级选牌→装备养成→名将 BOSS→结算→局外养成的完整循环，桌面与手机均可玩。
2. **确定性与性能解耦的引擎底座**：逻辑固定 60Hz tick + 渲染满帧插值；任意帧率、画质档位、设备下游戏性参数（刷怪、弹幕、掉落、数值、波次、BOSS）逐 tick 完全一致，为联机就绪提供可验证基础。
3. **联机就绪但本次不落地真实网络**：多玩家实体模型、控制源抽象、主机权威与快照/预测接口、本地 AI 影子玩家 + Loopback 模拟全部交付；真实 WebRTC/WS 传输仅定义接口边界。

## 2. 核心玩家故事（6 条）

1. 作为手游玩家，我想用虚拟摇杆 + 技能按钮单手割草，以便在通勤路上打完一局 8 分钟。
2. 作为三国粉丝，我想从 40 位武将中挑选并使用专属 Q 版形象出战，以便用喜欢的武将战斗。
3. 作为 Roguelike 玩家，我想在升级时从随机卡牌中选技能/属性，以便每局搭出不同 Build。
4. 作为养成玩家，我想通过 13 槽装备、宝石、魔盒、传说宝石打造 Build 并查看属性来源明细，以便量化比较每次提升。
5. 作为挑战型玩家，我想击败 8 位名将 BOSS、解锁无尽模式并冲本地 Top10，以便获得长期目标。
6. 作为开发/测试者，我想在同一 seed 下任意帧率与画质都能复现逐 tick 一致的战斗，以便保证公平性与后续可联机。

## 4. 验收清单（可勾选）

### 4.1 设计稿实施阶段 P0→P8 验收标准

**P0 — 脚手架 / ECS 基础 / 网络基础**
- [ ] 组件工厂单测通过

- [ ] `npm run dev` 与 `npm run build` 正常

**P1 — World / pools / scheduler / StatResolve / 网络组件**
- [ ] 属性金标准单测通过（ADD / MUL / MAX / OVERRIDE / MUTEX / CONDITIONAL）
- [ ] NetId↔eid 往返与回收单测通过

**P2 — 内容配置 / 存档结构 / 控制源**
- [ ] 注册表完整性校验通过（40 将等全内容）
- [ ] 1 真人 + 2–3 影子共享玩家组件与系统
- [ ] 控制源切换测试通过

**P3 — 战斗核心 / 时钟 / 敌人多目标**
- [ ] 确定性 tick 测试：同 seed 下，不同帧抖动与不同画质档位，tick N 的敌人数 / 状态 / 掉落完全一致
- [ ] 300 敌 / 500 弹幕场景渲染 ≥50 FPS

**P4 — 效果管线 / 装备宝石 / 权威与快照**
- [ ] 热路径零分配（分配观测无新增分配）

- [ ] Loopback host↔client 消息闭环
- [ ] 快照内容精确等于 `Replicated` 标签集合（不多不少）

**P5 — 魔盒 / 传说宝石 / 属性面板 / 预测和解**
- [ ] 传说宝石成功率与保底单测通过（含失败 +5%、成功重置）
- [ ] 属性详情面板与快照一致
- [ ] 和解测试：注入延迟/抖动后 N tick 内收敛

**P6 — 双模式 / BOSS / 排行 / codec**
- [ ] 首胜解锁持久化（刷新后保留）
- [ ] BOSS 配置可扩展（新增 BOSS 仅加配置）
- [ ] 本地 Top10 排行持久化
- [ ] 快照体积指标达标

**P7 — 移动端 / 渲染调优 / Host 迁移 / 存档归属**
- [ ] iPhone/Pixel 渲染 ≥45 FPS，且波次 / 敌人数 / 掉落与桌面逐 tick 一致
- [ ] 本地多 peer 模拟杀 Host → 最小 netId 接管，状态保真
- [ ] 只存本地玩家 meta（房间状态不入库）

**P8 — 测试与交付**
- [ ] 单测全绿
- [ ] 确定性 fuzz / 控制源切换 / loopback chaos（丢包、乱序、重复）通过
- [ ] Playwright E2E 全流程通过（选模式→选将→13 槽配装→属性核对→镶嵌→魔盒→战斗→升级→掉落→结算→养成→刷新存档）
- [ ] 存档体积 <80 KB
- [ ] 静态部署（`vite preview`）无 404

### 4.2 性能与游戏性解耦硬约束（DESIGN.md §2 / §13）

- [ ] 游戏性参数（敌人生成速率与同屏数、弹幕数量与速度、掉落表与掉率、伤害数值、波次时间轴、BOSS 行为）全部由配置与 tick 决定，与设备 / 帧率 / 画质档位无关
- [ ] 同一 seed 在模拟 30 / 60 / 144 fps 帧序列、不同 quality 档位下，跑相同 tick 数后的敌人数、生成序列、掉落、BOSS 阶段完全一致
- [ ] 不跳过任何 tick：低帧率下整体慢动作，但世界演化序列与高性能设备逐 tick 一致（无丢弃上限、不因帧率低削减）
- [ ] 渲染裁剪（Culled）仅跳过绘制，实体仍完整参与 AI / 碰撞 / 伤害 / 掉落
- [ ] 实体容量 CAP 固定（由波次最大同屏敌人数 + 弹幕上限 + 余量决定），所有设备统一，不随画质档位变化
- [ ] 低配模式仅渲染降级（Sprite 池替代 ParticleContainer、降分辨率与特效密度），不改变任何逻辑参数
- [ ] 画质档位（quality）只控制渲染层，不控制任何游戏性参数
- [ ] 确定性：相同 `(roomSeed, 输入序列)` → 逐 tick 完全一致（禁用 `Math.random`、关键处规避 sin/cos 平台差异、eid 不上线一律用 NetId）

## 5. 关键风险与待确认项

### 5.1 关键风险

| 风险 | 影响 | 缓解建议 |
| --- | --- | --- |
| 渲染性能（300 敌/500 弹幕 ≥50FPS、移动 ≥45FPS） | 验收不达标，且严禁靠削减实体达成 | 尽早做 Sprite/ParticleContainer 池化、`RenderSyncSystem` 只同步 dirty/位移；P3 前置压测 |
| 确定性易被破坏（浮点、sin/cos、排序不稳、eid versioning） | 逐 tick 一致与联机就绪失效 | 统一 Rng + 稳定排序 + 确定性 harness 前置；禁用 eid versioning |
| 联机范围被误扩大 | 团队误做 WebRTC/WS，超出本次范围 | 以 §2.6 为准，仅 ITransport 接口 + Null/Loopback |
| bitECS 0.4.x API 兼容（`createRelation`、手动回收、CAP 守卫） | 组件层返工 | 集中到 `src/ecs/bit/adapter.ts` 封装并锁定版本 |
| localStorage 容量 <80KB | 存档超限、写失败 | 结构精简 + 节流写；`QuotaExceededError` 提示拆解 |
| 40 将 + 全内容配置工作量巨大 | 进度关键路径 | 配置化与 Registry 先行，内容按 pack 并行填充 |
| 移动端多指命中与 `setPointerCapture` 各端差异 | 操作手感不一致 | 命中区 ≥44px、`touch-action:none`、iPhone/Pixel 实机验证 |

- **Q2 仓库状态**：工作区已 `git init` 且 DESIGN.md 已存在。是否需配置远端 / 首次提交策略？（实现侧默认在本地仓库推进）
